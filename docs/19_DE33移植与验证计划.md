# 19 · H618 DE3.3（DE33）DRM overlay 移植与验证计划

> 目标：在 **vendor 6.1（保留可用 HDMI/TCON/WiFi）** 上，把 DE33 的
> **VI overlay + NV12 + 硬件缩放 + CSC** 打通，使 GStreamer/cedrus 可以
> `硬解 → NV12 → overlay → HDMI`，不再经过 CPU `videoconvert`。
>
> 结论先说：**能做，但不是单点补丁**。上游 DE33 系列截至 7.4-rc1 **尚未完整合入**，
> 主线也没有 H616 HDMI/DE 节点；只能在 vendor 6.1 上做 backport/适配。

---

## 0. 现状与证据

### 0.1 已经确认的事实

| 实验 | 结果 |
|---|---|
| UI overlay `plane 41` + RGB | ✅ 彩条正常 |
| VI overlay `plane 31` + RGB | ✅ 彩条正常 |
| VI overlay `plane 31` + NV12（videotestsrc） | ❌ 黑屏 |
| VI overlay `plane 31` + NV12（cedrus） | ❌ 黑屏 |
| 硬件解码 900 帧 | ✅ 约 2s（~450fps） |
| 软件 `videoconvert` 到 BGRx 720p | ❌ ~20–25fps（瓶颈） |

所以：

- overlay/mixer 路由、z-order、HDMI 输出都正常；
- 问题集中在 **VI 层的 NV12/YUV 格式、scaler、CSC**；
- 硬件解码和硬件缩放能力本身存在。

### 0.2 vendor 6.1 的 DE33 是半成品

代码证据：

- `sun8i_mixer.c`：H616 cfg `is_de33=true`、`vi_num=1`、`ui_num=3`、`map={0,6,7,8}`；
- `sun8i_vi_layer.c`：格式选择只判断 `mixer->cfg->is_de3`，**没有 `is_de33` 分支**；
  H616 会走 **DE2 格式表/DE2 路径**，而不是 DE3/DE33 路径；
- `sun8i_csc.c`：有 `sun8i_de33_ccsc_set_coefficients()`，但地址/系数布局与上游不一致；
- `sun8i_csc_enable_ccsc()`：只处理 `is_de3`，**没有 `is_de33`**。

这解释了“RGB overlay 正常、NV12 黑屏”：RGB 不需要 CSC，NV12 进了未完成的路径。

### 0.3 上游状态（2026-11 核对）

- 主线 `v7.4-rc1` / `v6.18` 的 `sun8i_csc.c` **没有 DE33 代码**；
- `sun50i-h616.dtsi` 仍然**没有 HDMI/display-engine 节点**；
- DE33 支持仍是补丁系列（Ryan Walklin / Jernej Skrabec）：
  - [DE33 v11 系列](https://lists.freedesktop.org/archives/dri-devel/2025-May/506122.html)
  - [DE33 CSC 补丁](https://lkml.iu.edu/hypermail/linux/kernel/2511.1/11478.html)
  - [补丁串（2025-11）](https://patchew.org/linux/20251115141347.13087-1-jernej.skrabec@gmail.com/)
  - [DE33 layer refactor（2025-10）](https://lore-kernel.gnuweeb.org/linux-sunxi/20251012192330.6903-30-jernej.skrabec@gmail.com/)

**不能直接换主线内核**：主线没有 H616 HDMI；必须保留 vendor HDMI/TCON，再移植 DE33 mixer/layer/CSC。

## 1. 根因假设（按优先级）

### H1：`is_de33` 没有复用 DE3 的格式/scaler 路径（最可能）

vendor 代码里：

```c
if (mixer->cfg->is_de3)
    formats = sun8i_vi_layer_de3_formats;
else
    formats = sun8i_vi_layer_formats;
```

H616 的 `is_de3=false`、`is_de33=true`，于是用了 **DE2 格式表**。
DE2 表可能包含 NV12，但 **scaler/channel 配置不匹配 DE33**，导致“格式被接受但扫不出”。

**最小验证**：把 `is_de3` 判断改成 `is_de3 || is_de33`，并检查
`sun8i_vi_layer_update_coord()`、`sun8i_ui_layer_update_coord()`、
`sun8i_vi_scaler`/`sun8i_ui_scaler` 里的 DE3 条件分支。

### H2：CSC 地址/系数布局仍不对

上游 DE33 CSC：

```c
#define DE33_CCSC_BASE 0x800
#define DE33_CH_SIZE   0x20000
base = DE33_CCSC_BASE + layer * DE33_CH_SIZE;
SUN50I_CSC_COEFF(base, i) = base + 0x04 + 4 * i;   // 15 项
SUN8I_CSC_CTRL(base) = base + 0x00;                // BIT(0) enable
```

vendor 原实现用的是 `channel base - 0x200`，我们已按上游改过一次，
但仍黑屏——说明 **H1 可能同时存在**，不能只修 CSC。

### H3：VI layer 的 format→HW 映射/缩放器不匹配 DE33

`sun8i_mixer_drm_format_to_hw()`、`sun8i_vi_scaler` 的寄存器布局可能仍是 DE2/DE3 旧版；
DE33 的 scaler 通道/系数可能不同。

### H4：kmssink/DRM modifier 限制

即使 overlay 打通，cedrus 可能输出 **tiled NV12**；当前 `sun8i_layer_modifiers`
只有 `DRM_FORMAT_MOD_LINEAR`，kmssink 也不一定支持 modifier/DMA-BUF。
需要先让 cedrus 输出 **线性 NV12**（优先），或补 tiled modifier。

## 2. 两条路线

### 路线 A：最小补丁（先做，1–2 天）

目标：**不整体移植**，只修 H1/H2，让 `videotestsrc ! NV12 ! kmssink plane 31` 出彩条。

改动点：

1. `sun8i_vi_layer_init_one()`：
   ```c
   if (mixer->cfg->is_de3 || mixer->cfg->is_de33)
       formats = sun8i_vi_layer_de3_formats;
   ```
2. `sun8i_ui_layer_init_one()`：同样处理。
3. `sun8i_vi_layer_update_coord()` / `sun8i_ui_layer_update_coord()`：
   搜索所有 `is_de3`，确认 DE33 是否应走同一分支；至少 scaler/format 相关。
4. `sun8i_vi_scaler.c` / `sun8i_ui_scaler.c`：
   检查 `is_de3` 条件；DE33 的 scaler 可能沿用 DE3 布局。
5. `sun8i_csc.c`：保留我们已写的 **上游 DE33 0x800/15 项布局**；
   确认 `sun8i_csc_enable_ccsc()` 对 de33 不重复写。
6. `sun8i_mixer.c`：H616 cfg 显式 `.ccsc = CCSC_MIXER0_LAYOUT`（值 0，语义明确）。

验收（必须按顺序）：

```bash
# G1: UI overlay RGB
gst-launch-1.0 videotestsrc is-live=true ! \
  video/x-raw,width=1280,height=720,format=BGRx ! kmssink plane-id=41

# G2: VI overlay RGB
gst-launch-1.0 videotestsrc is-live=true ! \
  video/x-raw,width=1280,height=720,format=BGRx ! kmssink plane-id=31

# G3: VI overlay NV12（关键门槛）
gst-launch-1.0 videotestsrc is-live=true ! \
  video/x-raw,width=1280,height=720,format=NV12 ! kmssink plane-id=31
```

G3 出彩条 → H1/H2 解决，进入路线 B 的 G4；
G3 仍黑 → 直接转路线 B（整体移植）。

### 路线 B：移植上游 DE33 系列（1–2 周）

适用：路线 A 失败，或 G3 通过但 G4（cedrus 真流）失败。

步骤：

1. **建基线分支**
   ```bash
   git -C kernel/src/linux-6.1 checkout -b de33-port
   # 保存 vendor 原始 drm/sun4i 目录
   ```
2. **导入上游补丁**
   - DE33 mixer 配置 / `de_type` 枚举；
   - DE33 layer refactor（`sun8i_layer`、format/scaler/CSC）；
   - DE33 CSC 15 项实现；
   - 只取 `drm/sun4i` 相关，**不要**替换 vendor HDMI/TCON/CCU/DTS。
3. **适配 vendor API**
   - vendor 没有通用 `struct sun8i_layer`（各 layer 有 `mixer` 指针）；
   - 上游 refactor 可能引入 `layer->regs`、`lay_cfg`；需要把 vendor 的
     `sun8i_vi_layer`/`sun8i_ui_layer` 适配到新接口，或只 cherry-pick 逻辑函数。
4. **保留 vendor 显示链路**
   - `sun8i_dw_hdmi`、`sun8i_hdmi_phy`、`sun4i_tcon`、`sun8i_tcon_top` 不动；
   - 只替换 mixer/layer/CSC/scaler。
5. **逐 gate 验证**：G1→G2→G3→G4→G5。

## 3. 验证计划（Gate 制）

| Gate | 内容 | 通过标准 | 失败处理 |
|---|---|---|---|
| **G0** | 内核可启动、HDMI 有输出、SSH/串口可回滚 | `modetest -c` connected、能 SSH | 恢复 `.with-fbdev` 内核 |
| **G1** | UI overlay RGB | 彩条 | 查 mixer 路由 |
| **G2** | VI overlay RGB | 彩条 | 查 VI 通道/scaler |
| **G3** | VI overlay NV12（videotestsrc） | 彩条颜色正确 | 修 CSC/format/scaler |
| **G4** | cedrus NV12 → overlay（无 CPU 转换） | 720p30 彩条/视频，CPU < 30% | 查 tiled/modifier/DMA-BUF |
| **G5** | gmediarender 手机 DLNA 投屏 | 1080p/720p30，音画同步，1h 稳定 | 回退软件路径 |

### 3.1 G3 具体命令

```bash
# 板上
modetest -M sun4i-drm -s 51@49:1280x720
gst-launch-1.0 -v videotestsrc is-live=true ! \
  video/x-raw,width=1280,height=720,format=NV12 ! \
  kmssink plane-id=31
```

同时观察：

```bash
dmesg | tail -30
GST_DEBUG=kmssink:5 gst-launch-1.0 ...
modetest -M sun4i-drm -p
```

### 3.2 G4 具体命令

```bash
# 先生成 720p H.264 文件
gst-launch-1.0 -q videotestsrc num-buffers=900 ! \
  video/x-raw,format=I420,width=1280,height=720,framerate=30/1 ! \
  x264enc speed-preset=ultrafast tune=zerolatency ! \
  h264parse ! mp4mux ! filesink location=/tmp/test720.mp4

# cedrus 硬解 -> NV12 -> overlay
gst-launch-1.0 filesrc location=/tmp/test720.mp4 ! qtdemux ! h264parse ! \
  v4l2slh264dec ! video/x-raw,format=NV12 ! kmssink plane-id=31
```

如果这里报 “modifier not supported” 或花屏：

- 优先级 1：让 `v4l2slh264dec` 输出 **线性 NV12**（检查 V4L2 capture format，而不是 tiled）；
- 优先级 2：给 `sun8i_layer_modifiers` 加 `DRM_FORMAT_MOD_ALLWINNER_TILED`，
  并让 kmssink 支持 modifier/DMA-BUF；
- 优先级 3：临时用 `videoconvert` 仅做 detile（不是最终目标，但可验证 overlay）。

### 3.3 G5 具体命令

保持现有 `opiz3-renderer.service`，把 `--gstout-videopipe` 改为：

```
video/x-raw,format=NV12 ! kmssink plane-id=31
```

（不加 `videoconvert`/`videoscale`，缩放交给 VI scaler。）

## 5. 风险与决策点

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| H1 修完仍黑 | 中 | 路线 A 失败 | 转路线 B 整体移植 |
| 上游 refactor 与 vendor HDMI 冲突 | 高 | 编译/启动失败 | 只移植 mixer/layer/CSC，保留 vendor HDMI |
| CSC 寄存器仍不对 | 中 | NV12 色彩错/黑 | 对照 Android disp2/上游 patch |
| cedrus tiled 无法导入 | 高 | G4 失败 | 强制线性 NV12 或加 tiled modifier |
| kmssink 不支持 modifier | 中 | 无法零拷贝 | 改 GStreamer/kmssink 或用 v4l2convert |
| 时间超 2 周 | 中 | demo 延期 | 回退软件 720p / Android TV |

**决策点**：
- G3 在 3 天内不过 → 停止单点补丁，评估是否值得整体移植；
- G4 在 1 周内不过 → 放弃 Linux 硬件 overlay，转 Android TV/换板；
- 任何时候保留可回滚的软件 720p 方案。

## 7. Spike 执行结果（2026-11-05）

### 已通过

| Gate | 结果 |
|---|---|
| G1 UI overlay RGB | ✅ |
| G2 VI overlay RGB | ✅ |
| G3 VI overlay NV12（videotestsrc） | ✅（H1 + 上游 CSC 布局后） |
| G4 直出 1280×720 NV12 overlay（cedrus） | ✅ **CPU ~1%，流畅** |

关键补丁：

1. **H1**：DE33 复用 DE3 的格式表/alpha/颜色编码/VI scaler scale-mode：
   `if (is_de3 || is_de33)`；
2. **CSC**：按上游 DE33 布局
   `DE33_CCSC_BASE=0x800 + channel*0x20000`、`SUN50I_CSC_COEFF=base+0x04+4*i`、15 项系数。

### 未通过

- **任何缩放/定位都会出现横向花屏条纹**：
  - VI 硬件 scaler（`can-scale=true render-rectangle=...`）→ 横条；
  - 软件缩放到 404/416/1280 宽后再 overlay → 横条；
  - `videoscale` 输出 I420 → 解码器/链路报错；
  - 但 **原生 1280×720 NV12 直出全屏是干净的**。

结论：overlay + CSC 已打通；剩余问题缩小为 **DE33 VI scaler / 缩放后 buffer 的 pitch/stride/色度布局**。

### 下一步（按优先级）

1. 用 **原生 720×1280 NV12 → VI scaler 全屏拉伸到 1280×720**（不做部分宽度/偏移），判断 scaler 本身是否可用；
2. 若全屏 scaler 也横条 → 修 `sun8i_vi_scaler` 的 DE33 系数/scale-mode/寄存器；
3. 若全屏 scaler 干净 → 问题在部分宽度/`render-rectangle` 的 pitch/offset，需对齐 stride 或改用全屏 + 软件补边；
4. 检查 `GstVideoMeta` stride 与 DRM fb pitch，确认 32/64 对齐；
5. 最后再谈 gmediarender/phone 集成。

当前板子已恢复：fbdev 内核 + 软件 avdec 720p（颜色正确，20–25fps）。

### 7.1 scaler 判定结果

- 部分宽度 VI scaler（404/416/405 宽，x=0 或居中）→ 横向条纹；
- 全屏 VI scaler（720×1280 → 1280×720）→
  `drmModeSetPlane failed: No space left on device (28)`；
- 软件缩放到 NV12 再 overlay → 横向条纹；
- 原生 1280×720 NV12 直出 → 干净，CPU 1%。

推断：DE33 VI scaler 的 **缩放系数/scale-mode/输出 pitch 与 chroma plane 对齐**仍有问题；
720 高不是 32 的整数倍（720/32=22.5），NV12 的 chroma 偏移可能未按 32 对齐。
下一步可试：输出高度对齐到 736、或用全屏 compositor 生成 1280×720 NV12 再直出。

当前结论：**直出 overlay 已打通；缩放/letterbox 仍未打通**。

### 7.2 compositor / 软件 buffer 判定

- `compositor` 黑底 1280×720 + 视频 416×720 I420 → 全屏 overlay 仍横条；
- 只要 buffer 由 **videoscale/videoconvert/compositor** 生成，就横条；
- 只有 **cedrus 直出的 NV12** 全屏是干净的。

因此剩余问题拆成两个驱动级问题：

1. **DE33 VI scaler**：部分宽度横条，全屏缩放 `ENOSPC`；
2. **软件生成 buffer 的 chroma offset/pitch**：DE 按自己的对齐/偏移读取，和 GStreamer 的紧凑布局不一致。

修复方向：

- 修 `sun8i_vi_scaler` 的 DE33 系数/scale-mode/输出 pitch；
- 给 `kmssink`/GStreamer 加 **对齐的 NV12 分配器**（height 补到 32/64、chroma offset 对齐）；
- 或改用能输出 DE 对齐 buffer 的 V4L2 M2M/转换器（当前没有）。

这两项都不是应用层能解决的，属于 1–2 周驱动工作。

### 7.3 scaler 系数修复结果

修了 vendor `sun8i_vi_scaler_set_coeff()` 的两个实质 bug：

1. 垂直系数误用 `hstep`（应为 `vstep`）；
2. 色度步长未除以 `format->hsub/vsub`。

修复后 416×720 硬件缩放可以运行，但 **仍有横向条纹**。
说明除系数外，DE33 VI scaler 还存在 **pitch/phase/寄存器布局**层面的差异；
需要对照 DE33 scaler 寄存器/上游完整实现继续调，属于驱动级工作。

当前判断：直出 overlay 可用；缩放/letterbox 在 vendor 6.1 上仍未闭环。

### 7.4 进一步隔离（G7）

- 软件 NV12 拷贝 1280×720（不缩放）→ overlay **干净**：软件 buffer 布局没问题；
- VI scaler **1:1 强制使能**（1280×720 → 1280×720）→ **干净**；
- 只有**下采样缩放**（720×1280 → 416×720）→ 横条。

结论：问题在 **DE33 VI scaler 的下采样系数/phase/寄存器**，不是 buffer、不是 overlay、不是 CSC。
上游 “Assorted display fixes” 中两个相关补丁已应用：
- `vi scaler: Fix coefficient selection`（垂直用 vstep、色度除以 hsub/vsub）；
- `vi scaler: Restore opaque alpha`（GLB_ALPHA=0xff）。

仍横条 → 剩余差异需要 **全志 DE33 BSP 的 scaler 寄存器/系数表**，
或者完整的 DE33 scaler 实现；已超出上游公开补丁范围。

上游参考：
- <https://patchew.org/linux/cover.1785770165.git.jernej.skrabec@gmail.com/>
- <https://lkml.indiana.edu/hypermail/linux/kernel/2608.0/03719.html>

Linux 硬件 letterbox 目前的阻塞点：DE33 scaler 下采样；需要厂商寄存器资料。

## 8. 横屏直出（硬件 decode + NV12 overlay）结果

已实现并验证：

- `cedrus` 硬解 → NV12 → `kmssink plane-id=31` 全屏 1280×720；
- 手机横屏 B 站投屏有画面、有声，CPU 约 18%；
- 本地运动测试画面/声音正常。

但 `kmssink` 播放约 5–20 秒后停止，日志：

```text
kmsallocator: Failed to close GEM handle: Invalid argument 22
qtdemux: streaming stopped, reason not-negotiated (-4)
```

这是 kmssink 的 **DMABuf/GEM/framebuffer 泄漏/复用问题**（已知历史 bug），
不是解码/网络/overlay 路由问题。临时重启管线只能续播几秒。

解决选项：

1. 升级/打补丁 GStreamer `kmssink`（修复 GEM/fb 复用），2–4 天；
2. 换 `fbdevsink` 软件 RGB 路径（稳定，720p 约 20–25fps，CPU 高）；
3. 用自研 DRM 小应用复用 fb，绕开 kmssink（工作量大）。

当前生产回退：fbdev 内核 + avdec + fbdevsink 720p，稳定。

### 9. 分片 MP4 与 kmssink 的最终定位

- B 站 MP4 是分片 MP4；`qtdemux` 会在约 5 秒触发 `not-negotiated`，裸 H.264/MKV 可以稳定 30 秒；
- 用 `ffmpeg -c copy -f matroska -` 实时 remux 后，`fdsrc ! matroskademux` 能稳定 30 秒；
- 说明之前所谓 kmssink GEM 泄漏不是根因，根因是 **qtdemux 对分片 MP4 的 caps/segment 处理**；
- ffmpeg remux 方案已写入 bridge，但 no-fbdev 内核在一次重启后 HDMI 黑屏（连 modetest 测试图案也黑），
  切回旧 fbdev 内核 HDMI 正常。当前阻塞变成 **no-fbdev DRM/HDMI 初始化状态**，不是码流。

当前稳定回退：fbdev 内核 + 软件 avdec 720p，HDMI 正常。

## 10. 最终可用的 Linux 横屏直出方案

经过验证，稳定方案不是 cedrus 硬解，而是：

```text
gmediarender（仅 UPnP 发现/控制，fakesink）
  + bridge 读取 CurrentURI
  + ffmpeg 软件解码 → raw NV12 -> stdout
  + gst-launch fdsrc ! rawvideoparse ! kmssink plane-id=31
```

- 1280×720、30fps 横屏，实测稳定超过 30 秒；
- 手机横屏 B 站 URL 已跑通；
- CPU 约 1.5–2 核（ffmpeg ~70% + gst ~35%）；
- 无音频（当前 HDMI 屏无音频输出）；
- **不用 cedrus**：手机 H.264 流在约 6 秒会让硬件解码输出异常，kmssink `not-negotiated`；
- **不用 qtdemux**：B 站分片 MP4 会在约 5 秒触发 caps 问题；
- 固定 720p，不做缩放/letterbox。

服务：

- `opiz3-renderer.service`：fake gmediarender（enable）
- `opiz3-bridge.service`：ffmpeg + raw NV12 + kmssink（enable）
- 内核：no-fbdev H1（`/boot/Image -> vmlinuz-6.1.31-sun50iw9`）
- 启动参数：`video=HDMI-A-1:1280x720@60`

限制：仅横屏 720p；竖屏/其他分辨率不支持；无音频。
