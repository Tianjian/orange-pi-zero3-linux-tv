# 11 · H618 + USB 相机 + YOLO 640×480 的机器视觉理论性能分析

> 问题：Orange Pi Zero 3（Allwinner H618）用 USB 摄像头采集 **640×480 RGB**，跑 **YOLO** 目标检测，
> 理论性能到什么程度？瓶颈在哪？怎么选型/优化？
>
> 方法：用 SoC 峰值算力 + YOLO 的 FLOPs + A53 上实测可达到的有效效率（来自同代 A53 板卡的
> YOLO/ncnn/TFLite 基准）做**分层估算**：绝对上限（100% MAC）→ 现实区间 → 端到端（含 USB/预处理）。
> 所有实测锚点与 URL 见 [docs/evidence/yolo_benchmarks.md](evidence/yolo_benchmarks.md)；
> 计算过程可用 [scripts/yolo_perf_model.py](../scripts/yolo_perf_model.py) 复现。
>
> 结论先行：**H618 没有 NPU，GPU 在 Linux 下不能用于 CNN，性能上限由 4×Cortex-A53 @1.5GHz 决定。**
> 640×480 下：YOLOv5n 约 **2.6–5.0 FPS**（fp32）/ **5.0–9.3 FPS**（int8）；
> YOLOv8n 约 **0.6–1.2 FPS**（fp32）/ **1.2–2.3 FPS**（int8）；
> YOLOv5s/v8s 基本不具备实时性（≤1 FPS）。**USB2.0 相机不是瓶颈，CPU 推理才是。**

## 0. 结论速览

| 输入 640×480 | FLOPs* | 推理耗时（fp32） | FPS（fp32） | FPS（int8，×2.0） | 端到端延迟（int8） |
|---|---:|---:|---:|---:|---:|
| YOLOv5n | 1.43 G | 184–368 ms | **2.6–5.0** | **5.0–9.3** | 140–232 ms |
| YOLOv8n | 6.53 G | 843–1686 ms | **0.6–1.2** | **1.2–2.3** | 0.47–0.89 s |
| YOLOv11n | 4.72 G | 610–1221 ms | **0.8–1.6** | **1.6–3.1** | 0.35–0.66 s |
| YOLOv5s | 5.40 G | 698–1395 ms | 0.7–1.4 | 1.4–2.7 | 0.40–0.75 s |
| YOLOv8s | 21.45 G | 2771–5542 ms | 0.2–0.4 | 0.4–0.7 | 1.43–2.82 s |

\* FLOPs 按 640×640 官方值 × (640×480)/(640×640)=0.75 折算；fp32 有效效率按 **8–16%**
（≈3.9–7.7 GFLOPS，由 H618 160×160 实测 5.9 GFLOPS、H618 HPL 10.8 GFLOPS、RPi4/RPi3B 同代数据校准），
int8 按 **2.0×**（TFLite 整网 2.0–2.5×；A53 无 SDOT，纯 GEMM 只 +11%，收益主要来自权重/带宽减 4×）。
相机 30 fps、预处理 10 ms、后处理 5 ms；端到端 = 等一帧(33 ms) + 预处理 + 推理 + 后处理（未做流水线重叠）。

**一句话选型**：
- 要“能跑”：**YOLOv5n @640×480，int8，5–9 FPS**；或 **YOLOv8n @416×416，int8，2–4 FPS**。
- 要“实时”（≥10 FPS）：只能 **YOLOv5n @320×320 int8**（约 13–22 FPS，实际受固定开销限制约 10–18，小目标精度明显下降），或加 USB NPU。
- 要“高精度 + 实时”：**H618 做不到**，换带 NPU 的板（RK3566/RK3588/Jetson Orin Nano 等）。

## 1. 硬件基线（决定上限的三个数字）

| 项 | 规格 | 对 YOLO 的影响 |
|---|---|---|
| CPU | 4×Cortex-A53，最高 **1.512 GHz**（OPP 480/600/792/1008/1200/1296/1344/1512 MHz） | 唯一的通用算力；A53 是**顺序双发射、无 SMT**，IPC 低 |
| SIMD | ARMv8-A NEON 128-bit，**无 SDOT/UDOT 点积**（v8.0） | fp32 可用 4-lane FMA；int8 用 widening MAC：**纯 GEMM 算力仅 +11%**（BLIS U8GEMM 6.56 vs SGEMM 5.888 OPS/cycle），整网 2–2.5× 主要来自权重/带宽减 4× |
| FP32 峰值 | 4 核 × 8 FLOP/cycle × 1.512 GHz ≈ **48.4 GFLOP/s**（理论上限） | YOLOv5n 640×480 的 1.43 GFLOP 在 100% 利用率下 30 ms；YOLO 现实利用率 **8–16%**（H618 HPL 实测 10.8 GFLOPS 可作旁证） |
| GPU | Mali-G31 MP2，OPP 125/250/432/600/800 MHz，OpenGL ES 3.2 / Vulkan 1.1 / OpenCL 2.0（标称） | Linux 主线 **Panfrost 不提供 OpenCL**；厂商 5.4 blob 也没有可用的 YOLO 推理栈 → **实际不可用** |
| NPU | **无**（H616/H618 都没有 NPU） | 没有 INT8 TOPS 加速器；这是与 RK3566/RK3588 的本质差距 |
| 内存 | LPDDR4 32-bit，1/1.5/2/4 GB；带宽约 **12.8–19.2 GB/s**（1600/2400 MT/s） | 权重/激活带宽不是主要瓶颈（见 §2.3）；1GB 版本跑桌面+OpenCV 会紧张 |
| USB | 4×USB2.0（3 host + 1 OTG），**480 Mbps/口**，实际 ~30–40 MB/s | 640×480@30 的 YUYV 只要 18.4 MB/s，**够用**；RGB888 27.6 MB/s 偏紧 |
| 功耗/散热 | 整板满载约 **2.2 W**（实测），idle 1.7–1.8 W；满载温度 77–85°C | 实测 85°C 仍保持 1512 MHz（未见降频），但长期高温影响寿命/稳定性，仍建议散热片 |

> H618 与 H616 同 die 修订（L2 512KB→1MB，`docs/08` §1），所以 A53 的算力特征与 H616 完全一致。
> 1 MB L2 对 YOLO 的 depthwise 层有一定帮助，但不改变数量级。

### 1.1 为什么 GPU 不算数

- 主线内核的 Panfrost 只有 Vulkan/OpenGL，**没有 OpenCL**；Arm 的 OpenCL 驱动是闭源 blob，依赖厂商 5.4 内核与 X11/根文件系统，官方 Debian/Ubuntu 6.1 镜像不提供。
- 即使有 OpenCL，G31 MP2 的 FP32 峰值也只有 **~20.8 GFLOP/s @650MHz、~25.6 GFLOP/s @800MHz**（官方 8 FMA/cycle 推算；DTS OPP 最高 800MHz），且 CNN 在移动 GPU 上要高度调优（Winograd、纹理布局），
  在 4 GB 内存、无风扇的 Zero 3 上**投入产出比极低**。
- 结论：**按纯 CPU 评估**；GPU 只适合做显示/简单并行，不作为 YOLO 加速路径。

## 2. 理论算力模型

### 2.1 基本公式

```
t_infer = FLOPs(input) / (P_peak × η)          # η = 有效利用率
FPS     = min(camera_fps, 1000 / (t_pre + t_infer + t_post))
E2E     = 1000/camera_fps + t_pre + t_infer + t_post   # 未做流水线重叠
```

- `P_peak = 4 × 8 × 1.512 GHz = 48.4 GFLOP/s`（fp32，假设每核每 cycle 1 条 128-bit FMA）。
- `η`：A53 上 YOLO 的实测有效效率。**fp32 取 8–16%**（≈3.9–7.7 GFLOP/s），
  依据是同代 A53 板卡上 YOLOv5n 640 实测约 1.5–4 FPS 量级（等效 3–8 GFLOP/s，见 evidence 锚点）；
  int8 取 `η×2.0`（整网；纯算力收益只有 +11%，见 §2.4）。
- 这是“理论 + 实测校准”的区间，不是某一台机器的精确值；真机需用 §7 的方法实测。

### 2.2 输入 640×480 的 FLOPs

YOLO 官方 GFLOPs 都是 640×640。640×480 有两种用法：

1. **letterbox 到 640×640**：FLOPs 不变（按 640×640 算），白边浪费 25% 算力，但精度/后处理最稳。
2. **直接 640×480**（480 = 15×32，满足 stride 32）：FLOPs ≈ **0.75×**；需要重新导出模型/校准，
   精度通常略降（预训练都在 640×640）。

下表按 0.75× 折算（直接 640×480）：

| 模型 | 参数 | GFLOPs@640 | GFLOPs@640×480 | 权重 fp32/int8 |
|---|---:|---:|---:|---:|
| YOLOv5n | 1.9 M | 1.9 | **1.43** | 7.6 / 1.9 MB |
| YOLOv5s | 7.2 M | 7.2 | **5.40** | 28.8 / 7.2 MB |
| YOLOv8n | 3.2 M | 8.7 | **6.53** | 12.8 / 3.2 MB |
| YOLOv8s | 11.2 M | 28.6 | **21.45** | 44.8 / 11.2 MB |
| YOLO11n | 2.6 M | 6.3 | **4.72** | 10.4 / 2.6 MB |
| YOLO11s | 9.4 M | 21.5 | **16.12** | 37.6 / 9.4 MB |

> 注意：YOLOv8n 虽然参数比 v5n 少，但 GFLOPs 是 v5n 的 4.6 倍（C2f 结构），
> 在 CPU 上 **v8n 比 v5n 慢得多**；不要按参数量选型。

### 2.3 是算力瓶颈还是带宽瓶颈（roofline）

- 机器平衡点：`P_peak / BW = 48.4 / 12.8 ≈ 3.8 FLOP/Byte`。
- YOLO 的算术强度（含激活）大致 **20–100 FLOP/Byte**，远高于 3.8 → **compute-bound**。
- 权重每帧只需 1.9–45 MB，按 5 FPS、12.8 GB/s 计，权重带宽占比 <2%；激活流量约 0.2–0.5 GB/帧，
  对应 16–40 ms，占推理时间 10–20%。**结论：优化算力效率（量化/线程/算子）比优化内存更有效。**

### 2.4 实测锚点（η 的校准依据）

| 来源 | 平台/配置 | 数值 | 等效算力/说明 |
|---|---|---|---|
| [OPi-yolo-gpio-stream](https://github.com/AleksandrVechtomov/OPi-yolo-gpio-stream) | **Orange Pi Zero 3**，YOLO11n ncnn **160×160** fp32，640×480 采集 + ByteTrack + 绘制，端到端 | **66–71 ms/帧（14–15 FPS）** | 0.394 GFLOP / 66 ms ≈ **5.9 GFLOPS（峰值的 12%）**；外推到 640×480 ≈ 0.8 s/帧（1.3 FPS），与本文 0.35–0.66 s 的乐观端同量级 |
| [Computer Optics 2026 表 3](https://computeroptics.ru/KO/PDF/KO48-2/480211.pdf) | RPi 3B（4×A53 1.2GHz）TFLite **int8** | YOLOv8n 320→959 ms、512→2396 ms；YOLOv5n 320→647 ms | int8 整网比 fp16 快 2.0–2.5×；A53 1.2GHz 下 v8n@320 仅 2.3 GOPS 有效 |
| [Ultralytics RPi 指南](https://github.com/ultralytics/ultralytics/blob/3d3a2a7f4b3288529f4293e53f8e81193bc6166c/docs/en/guides/raspberry-pi.md) | RPi 4B（4×A72 1.8GHz）ncnn | YOLOv8n 640→**414.7 ms（2.4 FPS）** | 同板 ONNX RT 560 / TFLite 950 / PyTorch 1068 ms → **ncnn 最快** |
| [Qengineering](https://github.com/Qengineering/YoloV8-ncnn-Raspberry-Pi-4) | RPi 4B @1.95GHz，ncnn 4 线程仅推理 | YOLOv8n 640→322 ms（3.1 FPS） | 与上条同量级 |
| [sbc.compare H618 HPL](https://sbc.compare/orange-pi-zero-3) | Orange Pi Zero 3，HPL | **10.81 GFLOPS @ 2.2 W** | 峰值的 22%；说明“纯计算密集”能到 20%+，但 YOLO 的 depthwise/激活把 η 拉到 8–16% |
| [BLIS 2017](https://www.cs.utexas.edu/~flame/BLISRetreat2017/slides/Marat_BLIS_Retreat_2017.pdf) | Cortex-A53 SGEMM | **5.888 FLOP/cycle**（峰值 8 的 74%） | GEMM 极限；CNN 整体远低于此 |

> 结论：**8–16%（3.9–7.7 GFLOPS）是合理的 fp32 区间**，H618 的 160×160 实测中心值 12% 落在区间内；
> 640×480 的直接实测尚未公开，本文的 640 结果是“按 FLOPs 线性外推 + 同代板校准”，必须上板复核（§7）。

## 3. USB 相机与预处理预算

### 3.1 带宽

| 格式（640×480） | 每帧 | 30 fps 带宽 | USB2.0 余量 |
|---|---:|---:|---|
| RGB888 | 0.88 MiB | **27.6 MB/s** | 偏紧（其他 USB 设备会抢带宽） |
| YUYV 4:2:2 | 0.59 MiB | **18.4 MB/s** | 舒适 |
| MJPEG（Q80，约 40 KB/帧） | 0.04 MiB | **1.2 MB/s** | 很宽裕，但 CPU 要解码 |
| MJPEG（约 100 KB/帧） | 0.10 MiB | 3.0 MB/s | 宽裕 |

> USB2.0 理论 60 MB/s，UVC 实际 30–40 MB/s。**一台 640×480@30 的相机不会把 USB 跑满**，
> 但 RGB888 + 第二台 USB 设备/存储盘同时工作时要小心。
> 多数 UVC 模块输出 **YUYV 或 MJPEG**，不是 RGB888；RGB 是主机侧转换出来的。

### 3.2 每帧 CPU 预算（A53 @1.5GHz，单核，量级估算）

| 步骤 | 耗时 | 说明 |
|---|---:|---|
| UVC 驱动/URB + V4L2 DQBUF | 1–3 ms | mmap 缓冲，避免额外 memcpy |
| MJPEG 解码（若用 MJPEG） | 3–10 ms | libjpeg-turbo NEON；YUYV 则省掉 |
| YUYV→RGB | 1–3 ms | 可用 libyuv/NEON；UVC 也可能直接给 RGB |
| resize/letterbox 到 640×640 或 640×480 | 1–3 ms | 双线性 |
| 归一化 + HWC→CHW（fp32） | 3–8 ms | 921k×3 次乘加/转换；int8 量化更快 |
| 后处理（解码 + NMS） | 3–6 ms | 640 输入约 8400 个候选框 |
| **合计（不含推理）** | **10–25 ms** | 相对推理（200–7000 ms）很小，但会占一个核 |

> 相机帧间隔 33 ms（30 fps）。如果推理 200 ms，相机侧必须**丢帧取最新帧**，
> 否则队列会累积延迟（V4L2 只保留 2–4 个 buffer，DQBUF 前先 flush）。

### 3.3 采集→推理的延迟构成

```
曝光/读出 10–30 ms → USB 传输 5–20 ms（YUYV）或 1–3 ms（MJPEG）
→ 驱动/拷贝 1–3 ms → 解码/色彩/缩放 5–15 ms → 推理 200–7000 ms → NMS 3–6 ms
```

端到端主要被推理吃掉；相机侧优化只能省 20–40 ms，**不要指望它把 1 FPS 变成 5 FPS**。

## 5. 瓶颈判定与敏感性

以 **YOLOv5n @640×480 int8（5.0–9.3 FPS）** 为基准：

| 变化 | 影响 | 结果 FPS |
|---|---|---|
| 只跑 3 个核（留 1 核给相机/系统） | 算力 ×0.75 | 3.8–7.0 |
| 无散热片/高温环境 | 实测 85°C 未降频；若触发保护则 ×0.8 | 4.0–7.4（正常） |
| letterbox 到 640×640（+33% FLOPs） | 算力需求 ×1.33 | 3.8–7.0 |
| 相机 15 fps（省电/降带宽） | 只影响等待时间 | FPS 不变，E2E 少 33 ms |
| MJPEG→YUYV（省解码） | 预处理 −3~10 ms | FPS +0.1–0.3 |
| int8 量化精度损失 | mAP 通常 −1~3 个点（需校准） | FPS ×2.0 |

**主瓶颈排序**：CPU 算力（>80% 时间） > 预处理/后处理（5–15%） > USB/相机（<5%）。
所以优化顺序是：**换更小模型 → int8 → 降输入 → 多核调度 → 相机格式**。

## 6. 优化路线（按性价比）

| # | 手段 | 预期收益 | 代价/风险 |
|---|---|---|---|
| 1 | **换 nano 模型**（v5n/v8n/11n） | v8n→v5n ≈ 4.6× | 精度下降，需重训/校准 |
| 2 | **int8 量化**（TFLite/ncnn，校准集 200–500 张） | 整网 **2–2.5×**（TFLite 实测）；纯 GEMM 只 +11%，收益主要来自权重/带宽减 4× | mAP −1~3；A53 无 SDOT，别期待 4× |
| 3 | **降输入**（416/320） | 1.8–3× | 小目标漏检；需重新导出/校准 |
| 4 | **4 线程 + performance governor** | +10–25% | 功耗/温度上升；相机线程要留核 |
| 5 | **V4L2 mmap + 最新帧** | 降延迟，不升 FPS | 需处理丢帧/时间戳 |
| 6 | **MJPEG 采集** | 降 USB 带宽/驱动拷贝 | 增加解码 CPU；需确认相机支持 |
| 7 | **ROI/运动门控 + 跟踪**（每 N 帧检测，中间用 KCF/ByteTrack） | 等效 2–5× | 工程复杂度；快速运动目标会丢 |
| 8 | **多模型级联**（小模型找 ROI，大模型复核） | 精度/速度折中 | 两个模型的内存/调度 |
| 9 | **USB NPU 加速棒**（Coral/Hailo） | 10–30×（模型兼容时）；Coral 在 USB2 上比 USB3 慢 **3.2×**（MobileNet v2 58.1 vs 18.2 ms） | USB2.0 带宽/延迟、驱动与量化工具链、功耗；Hailo 只有 M.2/PCIe，Zero3 不可用 |
| 10 | **GPU OpenCL** | 理论有限（G31 MP2 约 20.8–25.6 GFLOPS，仅 CPU 峰值的 43–53%） | 主线无 OpenCL；厂商 blob 不可维护 → **不推荐** |

> 现实建议：**YOLOv5n/v8n + int8 + 416×320/416×416 + 4 线程**，目标 **4–8 FPS**；
> 若业务要求 ≥15 FPS 且精度不能降，H618 不是合适平台。

## 7. 上板实测方案（把“理论”变成“实测”）

```bash
# 0) 固定频率/ governors，记录温度
sudo cpupower frequency-set -g performance 2>/dev/null || \
  echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
cat /sys/class/thermal/thermal_zone0/temp

# 1) 相机：确认格式/帧率/带宽（不跑模型）
v4l2-ctl -d /dev/video0 --list-formats-ext
v4l2-ctl -d /dev/video0 --set-fmt-video=width=640,height=480,pixelformat=MJPG \
         --set-parm=30 --stream-mmap --stream-count=300 --stream-to=/dev/null
# 观察实际 fps 与丢帧；YUYV 也测一遍
```

## 8. 不确定性与风险

1. **效率区间是实测校准值**，不同框架/算子实现差异大：ncnn 通常优于 OpenCV DNN 1.5–3×；
   TFLite int8 在 A53 上对 depthwise 更友好，但 YOLO 的 focus/slice 等算子可能退化。
2. **YOLOv8/11 的非方形输入**需要重新导出/校准；直接用 640×640 预训练权重会 letterbox，算力 +33%。
3. **热**：实测 85°C 仍维持 1512 MHz（未降频），但长期高温会加速老化、影响 TF 卡/相机稳定性；机箱内必须散热。
4. **1GB 内存版本**：桌面 + OpenCV + 模型可能 OOM；建议 headless + 2GB 以上。
5. **USB 带宽共享**：13pin 扩展的两个 USB 口与板载 USB-A 可能在同一控制器/总线上，
   同时接相机 + 存储盘时需实测。
6. **int8 精度**：YOLO 的检测头对量化敏感，必须用业务数据校准并复测 mAP；不保证“无损”。
7. **GPU/NPU 结论**：主线 Panfrost 无 OpenCL；厂商 blob 可能可用但不可维护；
   若必须用 GPU，需单独做 OpenCL 可行性验证（不在本分析保证范围内）。
8. **“理论性能”不含模型加载、画面编码/推流、业务逻辑**；实际部署要预留 20–30% 余量。

---

## 9. 结论

- **H618 的机器视觉定位是“低帧率、低分辨率、轻量模型”**：YOLOv5n/v8n 级别，640×480 下约 **0.4–9 FPS**，
  其中 **YOLOv5n int8 是性价比最高的可用点（5–9 FPS）**。
- **USB2.0 相机足够**：640×480@30 的 YUYV/MJPEG 只占 1–18 MB/s，瓶颈不在采集。
- **不要选 v5s/v8s 及以上**：640×480 下 0.2–2.7 FPS（int8），业务基本不可用。
- **要更高帧率**：降输入（320/416）+ int8 + 多线程 + ROI 门控；仍不够就换带 NPU 的平台或加 USB 加速棒。
- **所有数字需上板复核**（§7）；本分析给的是选型与预算依据，不是性能承诺。
