# 封面：对适配方案有直接影响的 10 条结论

> 每条给 1 个主 URL；展开论证见后面对应章节。**这 10 条是本文的"该做什么"结论**。

1. **不要把"主线已支持 Zero3"当成"主线可用"**：DTS 从 v6.6 就进主线（2023-10），但到 7.4-rc1 主线仍**没有 HDMI/DE 节点**，显示输出必须继续用厂商 BSP 显示栈。〔内核源码〕[sun50i-h616.dtsi@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h616.dtsi)
2. **如果走主线，最低选 6.18，实用选 7.0+**：补齐顺序是 thermal(6.9) → 音频 codec(6.15) → GPU 节点(6.18)/GPU 可用(7.0) → VPU(7.4)；6.6 只有串口/SD/USB/SPI Flash/网口/PMIC/watchdog/RTC。〔内核源码〕[H616 dtsi v6.6](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h616.dtsi?h=v6.6)
3. **DTS 可以直接抄主线**：`sun50i-h616-orangepi-zero.dtsi` + `sun50i-h618-orangepi-zero3.dts` 覆盖省电、LED、USB、SD、SPI Flash、PMIC、网口全部关键参数，唯一缺的是 **SDIO WiFi 节点（mmc1）**。〔内核源码〕[zero3 dts@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h618-orangepi-zero3.dts)
4. **WiFi 必须外挂驱动，且这是官方设计而不是缺陷**：模块 `CDW-20U5622-00` 里的裸片是 **AW859A**，驱动栈是展锐/Unisoc 的 `uwe5622_bsp_sdio + sprdwl_ng + sprdbt_tty`；主线没有该驱动、也没有任何 staging/patchew 排队迹象（只有 Armbian 的外置仓库）。〔厂商〕[armbian/uwe5622](https://github.com/armbian/uwe5622)
5. **我们自己写 DTS 时，mmc1 + rfkill + pwrseq 三件套照厂商树抄**：厂商 6.1 树里 `&mmc1 { vmmc/vqmmc/mmc-pwrseq/bus-width=4/non-removable }`，主线板级 DTS 里**完全没有**这段。〔内核源码〕本地 `kernel/src/linux-6.1/.../sun50i-h618-orangepi-zero3.dts:153`
6. **千兆网口三个参数一个都不能少**：`phy-mode = "rgmii-rxid"`、`allwinner,tx-delay-ps = <700>`、`motorcomm,clk-out-frequency-hz = <125000000>`；v6.6 的 DTS 缺前两个（当时网口"能拿 IP 但收不到包"）。〔内核源码〕[v6.6 DTS 与 master 的 diff](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h618-orangepi-zero3.dts?h=v6.6)
7. **PMIC 用 AXP313A，走 r_i2c@0x36，驱动 6.6 才进主线**；但主线的 **PMIC 中断 parent 至今（7.4-rc1）仍写成 `&pio`**，社区已报"新 pinctrl 下开机 hang"，我们要么带补丁、要么在 DTS 里改 `&r_pio`。〔内核源码〕[axp20x.c AXP313A_ID@v6.6](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/mfd/axp20x.c?h=v6.6)
8. **GPU 想用 Panfrost 必须 ≥7.0**（`default_pm_rt_data`）；6.18 有 GPU 节点但没有电源域时序，一用就 hang。厂商内核给的 GPU 是 `status="disabled"`，社区靠改 DTB 强开。〔内核源码〕[panfrost_drv.c@v7.0](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/gpu/drm/panfrost/panfrost_drv.c?h=v7.0)
9. **VPU 在 7.4 才落地，但厂商 6.1 树里已有 H616 变体**：`cedrus.c` 里 `allwinner,sun50i-h616-video-engine → sun50i_h6_cedrus_variant` 的写法可以直接借到我们自己的补丁里。〔内核源码〕本地 `kernel/src/linux-6.1/drivers/staging/media/sunxi/cedrus/cedrus.c:707`
10. **构建链是最确定的风险项**：orangepi-build 只支持 Ubuntu 22.04、强依赖 GitHub 下载内核、ATF 编译反复失败、4GB 版本编出来只有 2.47GB；Armbian 已经把 `orangepizero3` 归为 **社区维护（`.csc`）**，主线 current=6.18 / edge=7.3。〔厂商〕[orangepizero3.csc](https://github.com/armbian/build/blob/main/config/boards/orangepizero3.csc)

## 1. H618 与 H616：同一颗 die 的"改名+修订版"

### 1.1 结论

**同一颗 die，不是新芯片。** 三条互相独立的证据：

1. 主线 DTS 系列作者（Arm 的 Andre Przywara，2023-07）在 cover letter 里写："The SoC is now labelled H618 instead of H616, which apparently is the same, just with more L2 cache."〔内核源码〕[LKML: [PATCH 0/3] sunxi: Orange Pi Zero 3 DT support](https://lkml.iu.edu/hypermail/linux/kernel/2307.3/09307.html)
2. `sunxi-tools` 的 FEL 支持提交（Andre Przywara，2023-08-08）写得更硬："The Allwinner H616 ships in at least two die variants, sometime under a different name (H618, T507), but sometimes labeled as a normal H616. The die variants differ in their CPU cluster control subsystem, which affects the location of the RVBAR shadow register…" 判定方法：读 `VER_REG`，老 die 低 8 位 = `0x00`，新 die = `0x02`。〔厂商工具/社区〕[sunxi-tools soc_info.h 提交日志](https://browse.dgit.debian.org/sunxi-tools.git/log/soc_info.h)（该页有 JS 反爬，正文摘自检索索引，未逐字校对页面）
3. linux-sunxi 邮件列表（2024-02，Andre Przywara 回复 H618 USB 性能问题）："the H616 and H618 are basically the same chip, with some very minor implementation differences, and with the H618 having **1MB of L2 cache instead of just 512KB**."〔内核源码/邮件列表〕[mail-archive: Re: H618 USB "Performance" Issues](http://www.mail-archive.com/linux-sunxi@googlegroups.com/msg35659.html)

也就是说：**H618 = 同一 die 的新修订（新 cluster 控制子系统 + L2 翻倍），可以用 `VER_REG` 区分；封装、引脚、外设地址空间不变。** 这条对我们是好消息：H616 的 DTS/pinctrl/驱动在 H618 上语义一致，`compatible = "allwinner,sun50i-h618"` 只是给板子一个更精确的名字，SoC 级 dtsi 仍然复用 `sun50i-h616.dtsi`。

### 1.2 官方口径对比（H616 产品简介 vs H618 产品页）

数据来源：本地 `docs/source/h616-soc.pdf`（官方 H616 产品简介，2 页）〔官方〕+ Allwinner H618 产品页〔官方〕[H618 产品页](https://www.allwinnertech.com/index.php?c=product&a=index&id=89&solveid=41) + Allwinner 2026 版选型册〔官方〕[Allwinner 产品选型 PDF](https://www.allwinnertech.com/uploads/download_source/20260303162657a4.pdf)。

| 项目 | H616（官方 brief） | H618（官方产品页/选型册） | 差异判定 |
|---|---|---|---|
| CPU | 4×Cortex-A53 64-bit（brief 未给频率） | 4×Cortex-A53（官方页/选型册也未给频率） | **无差异**；1.5GHz 来自板厂手册与 Armbian `CPUMAX=1512000` |
| L2 Cache | brief 未写（社区/内核口径 512KB） | 内核开发者口径 **1MB** | **真实差异**（唯一硬差异） |
| GPU | Mali-G31 **MP2**，OpenGL ES 3.2/2.0/1.0、Vulkan 1.1、OpenCL 2.0 | Mali-G31（未标 MP2；Zero3 手册写 MP2） | 无差异（同一 IP） |
| 视频解码 | H.265 Main10@L5.1 **4K@60 或 6K@30**；VP9 4K@60；AVS2 4K@60；H.264 4K@30 | H.265 **8K@24**；H.264/VP9/AVS2 **4K@30** | **官方口径冲突**，见 §1.3 |
| 视频编码 | H.264 4K@25 或 1080p@60；JPEG 1080p@60 | H.264 4K@25；JPEG 1080p@60 | 无差异 |
| HDR | HDR10、HLG | HDR10、HDR10+、HLG、**HDR Vivid** | 官方口径差异（软件/画质引擎层，未见硬件证据） |
| 显示 | HDMI 2.0a 4K@60 + TV CVBS；DE3.3、SmartColor3.3 | HDMI 4K@60 + TV CVBS | 无差异 |
| 内存 | 32-bit DDR4/DDR3/DDR3L/LPDDR3/LPDDR4，**最大 4GB** | DDR3/3L/LP3 + DDR4/LP4（未写上限） | 无差异（Zero3 有 1/1.5/2/4GB 四档） |
| 封装 | **TFBGA 284 balls，14×12mm，0.65mm pitch** | 分销商目录：**TFBGA-284，12×14mm，P0.65**〔厂商/分销〕[JLCPCB H618](https://jlcpcb.com/partdetail/AllwinnerTech-H618/C19189292)、[EasyEDA H618](https://easyeda.com/component/8e0106b5835b4001a588a7fbd5f50b52) | **无差异**（同封装同 ballout） |
| 外设 | USB2.0 OTG×1 + HOST×3、GMAC(RGMII/RMII)、SDIO3.0、UART×6、TWI×6、SPI×2、PWM×4、LRADC、CIR、TSC | 同左（接口栏逐项一致） | **无差异** |
| 软件 | brief 未写（第三方资料称 Android 10） | Android（H618 常配 Android 12） | 官方产品页只写 "Android"，Android 12 是盒子厂口径〔未证实〕 |

**对 Zero3 的推论**：Zero3 的 `compatible` 用 `allwinner,sun50i-h618`（板级），SoC dtsi 用 `sun50i-h616.dtsi`——主线自己就是按"同一颗芯片"处理的。

### 1.3 8K@24 的冲突：官方说 8K，brief 说 6K，实测没人证

- H618 官方页/选型册：`H.265 - 8K@24fps`。〔官方〕
- H616 官方 brief：`H.265 Main10@L5.1 decoder up to 4K@60fps **or 6K@30fps**`，并强调 "Maximum 6K@30fps H.265 decoding performance"。〔官方〕
- CNX Software 当年就质疑："I remain skeptical on everything that's written about the H618. For starters, there's no such thing as 6K media."〔社区〕[CNX: Allwinner H618 processor powers Android 12 TV boxes](https://www.cnx-software.com/2022/07/30/allwinner-h618-processor-powers-android-12-tv-boxes/)
- 泄露的 H618 datasheet 开头反而写 "supports **4K decoding** for OTT and IPTV markets"〔未证实〕[16rd 论坛 H618 Datasheet 附件页](https://bbs.16rd.com/forum.php?mod=attachment&aid=MjYxMDQyfGYzY2U5YjE4fDE3ODM0OTA0Njd8MHw2MzQ1NjA%3D&nothumb=yes)（需登录，仅读到索引摘要）。

**判定：8K@24 属于营销口径，没有独立实测证据；同一 VPU IP 在两个 brief 里给出 6K@30 与 8K@24 两种数字，实际能力大概率被 DDR 带宽与 VE 时钟限制。对我们的影响：不要把 8K 解码写进方案承诺。**

### 1.4 频率与 DVFS

- Armbian 的 sun50iw9 家族配置写死 `CPUMAX=1512000`（1.512GHz），并配 `GOVERNOR=ondemand`〔厂商〕[sun50iw9.conf](https://raw.githubusercontent.com/armbian/build/main/config/sources/families/sun50iw9.conf)。这从侧面确认 **H618 的量产频率上限是 1.5GHz 档**，不是某些盒子宣传的 1.8GHz。
- 主线 DTS 到 6.12 才引入 `sun50i-h616-cpu-opp.dtsi`（CPU OPP 表 + `cpu0.cpu-supply = <&reg_dcdc2>`）〔内核源码〕（v6.6/v6.8 的 zero3 dts 里 `cpu-opp` 出现次数为 0，v6.12 为 1）。
- Armbian 至今仍维护一个 DVFS 补丁：主线有 OPP 表但缺少厂商那种"电压爬坡（ramping）"，Armbian 用补丁把 ramp 加回去，理由是 OPI Zero2W 上 WiFi 负载会触发 cpufreq 崩溃〔厂商〕[armbian/build PR #10316: Refactor DVFS patch and clean up uwe5622 driver kernel configuration](https://github.com/armbian/build/pull/10316)。

### 2.3 逐版本 dtsi 体积（侧面反映补全速度）

| tag | `sun50i-h616.dtsi` 字节 |
|---|---|
| v6.6 | 19,035 |
| v6.9 | 22,851 |
| v6.12 | 25,483 |
| v6.15 | 25,877 |
| v6.18 | 26,511 |
| v7.0 | 27,685 |
| v7.3 | 28,917 |

> 读法：6.6→6.9 补了约 3.8KB（thermal、crypto、更多外设），之后进入"挤牙膏"阶段；**最后一块 4KB 里装的就是 VPU 节点与显示相关准备**。这也解释了为什么"Zero3 主线能开机"从 6.6 就成立，而"Zero3 主线能当桌面用"到 2026 年底仍不成立。

## 3. 无线：UWE5622 / AW859A / XR829 到底是什么关系

### 3.1 三方证据的真相

原理图第 7 页写 `AW859A`，手册 1.4 写 `20U5622`，SDK 里装的是 `uwe5622_bsp_sdio/sprdwl_ng/sprdbt_tty`（`docs/00`/`docs/02` 的 R1 已把三方冲突记录在案）。**主线情报的结论是：三个名字指同一套东西，不是三个候选芯片。**

- OpenWrt issue 标题就是 "Wi-Fi (**AW859A**) Not Detected on Orange Pi Zero 3 with OpenWrt 24.10.0"，正文写 "…AW859A (aka **CDTech 20U5622**)…"〔社区实测〕[openwrt/openwrt#18494](https://github.com/openwrt/openwrt/issues/18494)

### 3.2 主线有没有驱动？没有，而且短期内看不到进主线的路径

- 主线 `drivers/net/wireless/` 下**没有** `uwe5622`/`sprdwl`/`aw859a`（我用 `sun50i-h616` 相关树核对；H616 家族主线 DTS 里连 SDIO WiFi 节点都没建）。
- 厂商 SDK 的 BSP 内核里有一个 88 个 `.c` 文件的大驱动：`drivers/net/wireless/uwe5622/{unisocwcn,unisocwifi,tty-sdio}`〔内核源码/本地〕`kernel/src/linux-6.1/drivers/net/wireless/uwe5622/`。
- 社区把它抽成独立仓库 `armbian/uwe5622`，用 **DKMS** 支持 6.1 / 6.12 / 6.18 / 7.0 / 7.1，提供 `uwe5622_bsp_sdio`、`sprdwl_ng`、`sprdbt_tty` 三个模块，Allwinner 变体要 `CONFIG_AW_WIFI_DEVICE_UWE5622=y`〔厂商〕[armbian/uwe5622 README](https://github.com/armbian/uwe5622)。
- 有人试过把它硬塞进主线：`Doct2O/orangepi-zero3-mainline-linux-wifi` 把驱动打进 6.5.3，README 里留着典型失败现场：`invalid module format`、`Unexpected kernel BRK exception at EL1`、`wcn_bind_verify_calculate_verify_data` 处非法指令〔社区实测〕[Doct2O 仓库](https://github.com/Doct2O/orangepi-zero3-mainline-linux-wifi)。

### 3.4 我们该记的三条操作事实

1. **判定实物**：`cat /sys/bus/sdio/devices/*/device`、`dmesg | grep -iE "uwe5622|sprdwl|aw859|2355"`、`lsmod`。SDIO 上出现 `2355`（Marlin3L）系即 UWE5622/AW859A。
2. **固件路径**：`/lib/firmware/wifi_2355b001_1ant.ini`（+ BT 固件）。固件随驱动一起分发（Armbian/Debian 侧叫 `uwe5622-firmware`，OpenWrt 侧是 `uwe5622-firmware` 包，内核补丁与固件都取自 Armbian），**我们打包时直接复用，不要自己造 ini**〔厂商〕[DeepAQ/openwrt-uwe5622-sunxi](https://github.com/DeepAQ/openwrt-uwe5622-sunxi)。
3. **DTS 要自己补**：`&mmc1`（bus-width=4、non-removable、mmc-pwrseq、vmmc/vqmmc）+ `sunxi-rfkill` 节点（BT/WiFi 复位 GPIO）+ `&pio` 里 PG bank 1.8V 供电。主线一个都没有（见 §2.2）。

### 3.5 同一件事在三棵树里的落点对照

| 关注点 | 主线 master（7.4-rc1） | 厂商 6.1.31（`linux-orangepi`） | Armbian（current 6.18 / edge 7.3） |
|---|---|---|---|
| WiFi 驱动 | 无 | `drivers/net/wireless/uwe5622/`（88 个 `.c`） | 独立仓库 + DKMS（`uwe5622-allwinner` extension） |
| WiFi DT 节点 | **无 `&mmc1`** | `&mmc1`（pwrseq + 双路供电 + non-removable） | 随板级 patch 目录带入 |
| BT 服务 | 无 | `aw859a-bluetooth.service` 之类 | `sun50iw9.conf` 里 `systemctl enable aw859a-bluetooth.service` |
| 固件 | 无 | `wifi_2355b001_1ant.ini` 等 | 由 extension/包提供 |
| 显示栈 | 无 DE/HDMI 节点 | `display-engine` + `dw-hdmi` + `hdmi-phy` + `tcon-top` 全量 | 保留 BSP 显示补丁集（依赖内核分支） |
| VPU | 7.4 起有（驱动 + DT） | 有（`h616 → h6 variant` 映射） | 跟随所用内核分支 |

读法：**这三棵树的差异不是"新旧"，而是"职责划分"**——主线把"通用 IP 支持"做进 SoC dtsi/驱动，厂商把"板级 + 私有 IP"塞进板级 dts/私有驱动，Armbian 用"扩展 + 补丁目录 + 外置驱动仓库"把两者拼起来。我们要做的适配，本质上是决定**自己当哪一类**。

## 4. 有线与电源：YT8531C 与 AXP313A

### 4.1 Motorcomm YT8531C：主线原生支持，但"延迟三参数"必须对

- 主线 PHY 驱动 `drivers/net/phy/motorcomm.c` 里明确有 `PHY_ID_YT8531 0x4f51e91b`、`YT8531S 0x4f51e91a`，并支持 `motorcomm,clk-out-frequency-hz` 之类 DT 属性〔内核源码〕[motorcomm.c@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/net/phy/motorcomm.c)。
- Zero3 主线 DTS 的三处关键配置（可直接抄）：

```dts
&emac0 {
	allwinner,tx-delay-ps = <700>;   /* 6.7 起才有 */
	phy-mode = "rgmii-rxid";         /* 6.7 起才有 */
	phy-supply = <&reg_dldo1>;
};
&ext_rgmii_phy { motorcomm,clk-out-frequency-hz = <125000000>; };
&mdio0 { ext_rgmii_phy: ethernet-phy@1 { compatible = "ethernet-phy-ieee802.3-c22"; reg = <1>; }; };
```

- 历史教训：**v6.6 的 DTS 只有 `phy-supply`，没有 delay 参数**，于是首发补丁自己都写 "Ethernet is almost working, I get an IP address via DHCP, but no further packets come through. Might be either a problem with the new Motorcomm PHY driver, or some missing delay settings"〔内核源码〕[LKML cover letter](https://lkml.iu.edu/hypermail/linux/kernel/2307.3/09307.html)。v6.7 起 `tx-delay-ps=700` 与 `rgmii-rxid` 补齐（我用 tag 逐个核对：v6.6=0 处，v6.7=1 处）。
- 结论：**如果我们自己写 DTS 却漏了 tx-delay，症状就是"能 DHCP 不能传数据"，很容易被误判成驱动 bug**。这是移植时最贵的一个坑。

### 4.2 AXP313A：6.6 进主线，但中断 parent 有已知 bug

- mfd：`drivers/mfd/axp20x.c` 里 `AXP313A_ID`、`axp313a_writeable_ranges`、PEK 资源全套（v6.5 grep=0，**v6.6 grep=2**）〔内核源码〕[axp20x.c@v6.6](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/mfd/axp20x.c?h=v6.6)。
- regulator：`drivers/regulator/axp20x-regulator.c` 在 v6.6 已有 26 处 AXP313A 相关代码（DCDC1/2/3 + ALDO1 + DLDO1）〔内核源码〕。
- 访问方式：Zero3 用的是 **`r_i2c`（i2c@7081400）地址 0x36**，不是 RSB；三条 vin 都接 5V，`dcdc1`=GPU/系统、`dcdc2`=CPU、`dcdc3`=DRAM、`aldo1`=1.8V(PLL/PG)、`dldo1`=3.3V(IO/TF/WiFi)〔内核源码〕[zero3 dts@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h618-orangepi-zero3.dts)。
- **已知未修 bug**：2026-03 的补丁指出 AXP313 中断实际接在 **PL bank（R_PIO）**，而 DTS 写成 `interrupt-parent = <&pio>` + `interrupts = <2 9 …> /* PC9 */`；在 `pinctrl: sunxi: Implement gpiochip::get_direction()`（commit `01e10d0272b9`）之后，中断建立时会走错 pinctrl 实例 → **invalid register access，开机 hang**〔内核源码〕[patchew: arm64: dts: allwinner: fix Orange Pi Zero 3 PMIC interrupt routing](https://patchew.org/linux/20260308-rc2-boot-hang-v1-0-d792d1a78dfd@mmpsystems.pl/)。
- 我在 **7.4-rc1** 的 Zero3 DTS 里核对：`interrupt-parent` 仍然是 `&pio`，`/* PC9 */` 注释仍在——**说明该修复截至 2026-11 尚未进主线**。→ 我们的 BSP 如果升级到带新 pinctrl 的主线，必须自带这个修正（改成 `&r_pio` 并把 cells 改成 PL 的编号）。

## 5. GPU 与 VPU：为什么"有驱动"≠"能用"

### 5.1 GPU：Panfrost 支持 Bifrost G31，但 H616 的**电源域时序**是 2025 年才补的

时间线：

| 时间 | 事件 | 证据 |
|---|---|---|
| 2023-07 | 主线 H616 dtsi **没有 GPU 节点**（v6.6 里 `h616-mali` grep=0） | 〔内核源码〕 |
| 2025-04 | Philippe Simons 发 `[PATCH v2 0/3] drm/panfrost: enable G31 on H616`：问题描述极准——"H616 有一个专用 power domain；probe 后 GPU 进入 runtime suspend 会关掉 power domain，**首次使用 GPU 时再开 power domain 会 hang 死系统**"；方案是"开关时钟/复位必须排在 power domain 之后/之前" | 〔内核源码〕[LKML v2 cover](https://lkml.iu.edu/2504.0/03285.html)、[lkml.org 讨论](https://lkml.org/lkml/2025/4/28/178) |
| v6.18 | dtsi 里出现 `gpu@1800000` + `power-domains = <&prcm_ppu 2>`；Zero3 DTS 加 `mali-supply`；但 `panfrost_drv.c` 仍用 `default_data`（**无 PM_RT 处理**） | 〔内核源码〕（tag 逐个 grep：v6.18 `default_pm_rt_data`=0） |
| v7.0 | `panfrost_drv.c` 里 `{ "allwinner,sun50i-h616-mali", &default_pm_rt_data }`，PM runtime 时序落地 | 〔内核源码〕[panfrost_drv.c@v7.0](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/gpu/drm/panfrost/panfrost_drv.c?h=v7.0) |

厂商侧：BSP 内核的 dtsi 有 GPU 节点但**默认 `status="disabled"`**，且没有 mainline 的 OPP/电源域配套；社区的通用做法是"反编译 dtb → 把 gpu 的 disabled 改 okay → 重新编译覆盖 `/boot/dtb/allwinner/sun50i-h616-orangepi-zero3.dtb` → 加 xorg panfrost 配置 → `glmark2` 验证"〔社区实测〕[B 站：香橙派 Zero3 启用 panfrost GPU 加速](https://m.bilibili.com/opus/944197673520463945)（步骤可信，但未给帧率/稳定性数据，属"能点亮"级别）。

**对适配方案的含义**：想要 GPU 加速，只有两条路——(a) 内核 ≥7.0 用主线 panfrost；(b) 自己把 §5.1 那 3 个补丁 + `power-domains`/`mali-supply` 移植到 6.18。**在任何 <6.18 的内核上谈 GPU 都是空谈（节点都没有）。**

### 5.2 VPU：Cedrus 支持 H616 是 2026-10 才合并的

| 事实 | 证据 |
|---|---|
| 7.4-rc1（master）`cedrus.c` 才有 `allwinner,sun50i-h616-video-engine`，映射到 `sun50i_h6_cedrus_variant`；v6.12/6.15/6.18/6.19 **都没有** | 〔内核源码〕[cedrus.c@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/staging/media/sunxi/cedrus/cedrus.c)（逐 tag grep：h616 compatible 计数 0/0/0/0） |
| 同一时间 dtsi 才加 `video-codec@1c0e000`（带 `iommus`、`allwinner,sram`） | 〔内核源码〕[sun50i-h616.dtsi@master](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/arch/arm64/boot/dts/allwinner/sun50i-h616.dtsi) |
| 补丁系列是 Chen-Yu Tsai 的 `[PATCH v3 0/7] arm64: allwinner: h616: Support Video Engine`，2026-10-06 被 "Applied to sunxi/dt-for-7.4" | 〔内核源码〕[lkml.org 归档](https://lkml.org/lkml/2026/10/6/52)、[v1 cover（2026-05）](https://lkml.iu.edu/hypermail/linux/kernel/2605.0/05652.html) |
| 厂商 6.1 树**早就有** h616 变体（`cedrus.c:707` 直接复用 h6 variant） | 〔内核源码/本地〕`kernel/src/linux-6.1/drivers/staging/media/sunxi/cedrus/cedrus.c` |

**判定：VPU 硬件是存在的（H616/H618 同款 VE），但主线软件支持到 2026 年底才刚落地；厂商 BSP 通过"h616 → h6 variant"的偷懒映射 + 私有 dtsi 节点实现解码。我们如果把 `sunxi_cedrus` 编进 6.18 主线内核，会得到一个"驱动在、节点不在、什么都不 probe"的假象——这正是 §2.2 里 `video-codec` 一栏 v7.3 仍是 ✘ 的原因。**

### 5.3 HDMI/DE：主线的"最后一公里"卡了三年

- 事实：DE33 的 **mixer 支持**在 sun4i DRM 里已有（Ryan Walklin 的 PoC 后续），`clk: sunxi-ng` 也在 2025-05 加了 DE33 时钟支持〔内核源码〕[clk: sunxi-ng: ccu: add Display Engine 3.3 (DE33) support（commit be0e9a37）](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=be0e9a3727872783bad0752dc82e0857f4776049)。
- 但 `sun50i-h616.dtsi` 到 7.4-rc1 **一行 display 节点都没有**，所以"没有东西 probe"。
- 2025-10 Ryan Walklin 的 `[PATCH 00/30] drm/sun4i: Refactor layer code for proper DE33 support` 明确说这是"三个系列中的第一个"（层/混合器解耦、驱动重构）〔内核源码〕[lkml.org 2025/10/31](https://lkml.org/lkml/2025/10/31/301)。
- 2026-09 有人发 `[PATCH 0/2] arm64: dts: allwinner: h616: add HDMI device tree nodes`，声称"schematic 上 `sun50i-h618-orangepi-zero3.dts` 加 25 行即可在 Zero3 4GB 上跑 1920×1080@60 桌面"，Jernej Škrabec 回复指其缺少 DE/TCON 基础系列〔内核源码〕[LKML 2026-09 回复](https://lkml.iu.edu/hypermail/linux/kernel/2609.0/12266.html)、[PATCH 1/2 描述](https://lkml.iu.edu/2609.0/11842.html)。
- 厂商侧完整：本地 6.1 树 `sun50i-h616.dtsi` 有 `display-engine`（`allwinner,sun50i-h6-display-engine`）、`hdmi@6000000`（`sun50i-h616-dw-hdmi`）、`hdmi-phy@6010000`（`sun50i-h616-hdmi-phy`）、`tcon-top@6510000`，Zero3 DTS 里还有 `hdmi-connector`；Armbian 论坛日志里 `dw_hdmi_cec / display_connector` 都在加载〔内核源码/本地 + 论坛〕。

**结论：Linux 下 HDMI 输出在 2026-11 仍然是"厂商 BSP 专属"，主线不可用。这条对"Zero3 当桌面/媒体中心"的方案是硬约束。**

## 6. 官方 SDK 与发行版：6.1 内核到底是什么

### 6.1 官方 6.1（`orange-pi-6.1-sun50iw9`）= 主线 6.1.31 + 厂商 BSP 混合体

本地 `kernel/src/linux-6.1` 的直接证据（`docs/04` 已确认 SDK `next` 分支拉的就是这个分支）：

```
Makefile:  VERSION=6 PATCHLEVEL=1 SUBLEVEL=31
git remote: origin https://github.com/orangepi-xunlong/linux-orangepi.git
git log --oneline | wc -l  →  1        # 单条 squash 快照，历史被压平
唯一 commit: "opizero3/opizero2w: dts: rename h616 to h618"
```

- **是"主线派生"**：目录树、`arch/arm64/boot/dts/allwinner/`、`drivers/staging/media/sunxi/cedrus` 全部是主线形态，版本号 6.1.31 也对得上 LTS。
- **但被厂商大量"加料"**：`drivers/net/wireless/uwe5622`（88 个 `.c`）、`sun50i-h616.dtsi` 里的 DE/HDMI/TCON/ahub 节点、`sun50i-h618-orangepi-zero3.dts` 里的 `&mmc1` WiFi、`reg_vcc33_wifi`/`reg_vcc_wifi_io`/`wifi_pwrseq`、`ahub_dam_plat/ahub1_mach` 音频链路——这些在主线 6.1/6.6 里都不存在。
- **补丁量无法从 git 统计**（历史被压成 1 条 commit），只能从"体量"估：`uwe5622` 一个驱动 88 个 `.c`，加上 BSP 显示/音频/ISP/`sunxi-*` 系列驱动，属于**数千文件级别**的私有增量。这与"补丁只有几十个"的普通发行版内核不是一个量级，**把它当"主线 + 小补丁"来维护是不现实的**。
- 厂商 dts 里 `compatible = "xunlong,orangepi-zero3", "allwinner,sun50i-h616"`（注意是 **h616**，不是 h618），进一步说明 BSP 是把 H618 当 H616 用的——和 §1 的"同一颗 die"结论一致。

### 6.3 Armbian：事实上的"能用"基线

- 板级配置：`orangepizero3.csc` —— **`.csc` = community supported configuration（社区维护）**，维护者 `chraac`，`KERNEL_TARGET="current,edge"`，`OVERLAY_PREFIX="sun50i-h616"`，`BOOTCONFIG="orangepi_zero3_defconfig"`，`enable_extension "uwe5622-allwinner"`〔厂商〕[orangepizero3.csc](https://github.com/armbian/build/blob/main/config/boards/orangepizero3.csc)。
- 内核版本（2026-11 的 `sunxi64_common.inc`）：`legacy=6.12`、**`current=6.18`**、**`edge=7.3`**；U-Boot `tag:v2026.10`、ATF `lts-v2.14.11`〔厂商〕[sunxi64_common.inc](https://raw.githubusercontent.com/armbian/build/main/config/sources/families/include/sunxi64_common.inc)。
- U-Boot 侧的关键历史：以前自锁在 v2025.04，因为需要 H616 的 DRAM 补丁（"size-detection rework + 1.5GB"），这些补丁现在已上游，于是改用家族默认版本〔厂商〕同上 csc 注释。→ **这条直接对应"1GB 版本偶尔识别成 2GB / 1.5GB 变体"的老问题**，属于我们选 u-boot 版本时必须注意的点。
- Armbian 论坛的实测基线：`6.6.72-current-sunxi64`（2025-01）、`6.1.31-sunxi64`（2023-08），网口/WiFi/温度/负载均有截图〔论坛〕[Armbian 论坛 Zero3 主题帖](https://forum.armbian.com/topic/29202-orange-pi-zero-3/)。

### 6.4 OpenWrt：能启动，但 WiFi 默认缺席

- 24.10.0 镜像在 Zero3 上"能启动、无 wlan0"（issue #18494）；另有 24.10.0 无法启动的报告（#18087，日志中出现 `PMIC: Probing AXP305 on RSB` / `Could not init RSB: -65539`，因果关系未确认）〔社区实测〕。
- 社区自编镜像（ImmortalWrt master，6.18.55）加 `kmod-uwe5622 + uwe5622-firmware + wpad` 后 2.4G/5G 都可用〔社区实测〕[right.com.cn 帖](https://www.right.com.cn/forum/thread-8494582-1-1.html)。
- 结论：**OpenWrt 官方镜像不能作为"WiFi 可用"的参考基线**；它反而证明了"没有 uwe5622 驱动 = 没有 WiFi"。

## 8. 落到我们的适配方案（比封面更细的执行建议）

### 8.1 三条路线，按"要不要 WiFi/HDMI"分叉

| 路线 | 内核 | WiFi | HDMI/DE | GPU | VPU | 适合 |
|---|---|---|---|---|---|---|
| A. 厂商 BSP 为主 | 6.1.31 / 5.4 | ✔（BSP 内建） | ✔（BSP 内建） | 默认 disabled，可强开 | ✔（h6 variant 映射） | **要"整机可用"**，我们当前的主线选择 |
| B. 主线 6.18 LTS | 6.18 | △ 外挂 uwe5622 DKMS + 自写 mmc1 节点 | ✘ | ✘（有节点无时序） | ✘ | 只要串口/网口/存储的服务器场景 |
| C. 主线 7.x | 7.3/7.4 | △ 同上 | ✘（等 DE33 系列） | ✔ | ✔（7.4） | 追新、能接受无 HDMI |

### 8.2 具体动作清单（按优先级）

1. **DTS 底座**：以主线 `sun50i-h616-orangepi-zero.dtsi` + `sun50i-h618-orangepi-zero3.dts` 为底，补 4 段：`&mmc1`（WiFi）、`sunxi-rfkill`、`&ir`（若要红外）、显示栈（从厂商树搬 de/hdmi/tcon 节点，或整段用厂商 dtsi）。
2. **PMIC**：`axp313a` 保持 `r_i2c` 0x36，但**中断 parent 改 `&r_pio`**（或临时禁用 PMIC 中断）——否则新 pinctrl 下会开机 hang（§4.2）。
3. **以太网**：`rgmii-rxid` + `tx-delay-ps=700` + `clk-out-frequency=125MHz` 三件套写死，并在 CI 里加一条"`iperf3` 双向 30s 无丢包"的冒烟测试（防 §4.1 的"能 DHCP 不能传"）。
4. **WiFi**：走 `armbian/uwe5622`（DKMS）而不是抄 BSP 的 88 个文件；固件按 `wifi_2355b001_1ant.ini` 打包；上线前用 `dmesg | grep 2355` 确认固件版本匹配（否则出现 `length mismatch`）。
5. **GPU**：若必须加速，选 ≥7.0 或把 `default_pm_rt_data` 那 3 个补丁 backport 到 6.18；同时 `mali-supply = <&reg_dcdc1>`、`power-domains = <&prcm_ppu 2>` 两行不能漏。
6. **VPU**：6.1 BSP 直接用；若要 6.18，需同时 backport 驱动 compatible + dtsi `video-codec` 节点（只 backport 驱动无效）。
7. **HDMI**：2026-11 前不要指望主线；厂商 6.1 树 + `hdmi-connector` 是唯一成熟路径（Armbian 也仍在用 BSP 显示栈的补丁集）。
8. **构建**：Ubuntu 22.04 容器 + 预置工具链 + 内网镜像（GitHub 依赖是最大不确定项）；ATF 编译失败先看 `sun50iw9.conf` 的 `ATF_PLAT/ATFBRANCH`（§6.2）。
9. **u-boot/内存**：用带 H616 DRAM size-detection 修复的版本（Armbian 已上游化），并实测 1GB/1.5GB/4GB 三种板子；`cat /proc/meminfo` 与 `dmesg | grep -i dram` 双确认。
10. **回归基线**：`uname -r` + `dmesg` 里必须有 `motorcomm / dwmac-sun8i / sunxi_cedrus / panfrost(如启用)`；缺哪个就知道对应节没打通。

### 8.3 与既有文档的衔接

- `docs/01` 的"WiFi 20U5622"→ 本文升级为"模块 20U5622 / die AW859A / 驱动 UWE5622"三层表述，**建议 `docs/00`/`docs/02` 的待确认项 Q1 可以结案**（仍需上板读 SDIO id 做最终确认，但"型号矛盾"本身已有解）。
- `docs/02` 的 R1 结论"不做谁对的断言"→ 本文给出的是"两者都对，不是二选一"，可以把风险从"可能装错驱动"降级为"模块批次未排除"。
- `docs/04` 的编译流程 → 本文补充了 4 个真实 issue（#101 #149 + GitHub 依赖 + ATF），可作为"已知失败模式"章节的素材。
