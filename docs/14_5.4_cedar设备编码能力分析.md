# 14 · 5.4 BSP 的 cedar device 到底有没有编码能力？

> 对象：`linux-orangepi@orange-pi-5.4-sun50iw9` 的 `drivers/media/cedar-ve/`（源码摘录见
> `hardware/ref/cedar-ve-5.4/`），以及 H616/Zero3 的 5.4 DTS 绑定。
> 结论：**cedar device 暴露了“编码引擎所需的底层资源”（寄存器窗口、VENC 锁、编码 IRQ、时钟/复位、IOMMU/DMA-BUF），
> 但没有实现 H.264 编码，也没有提供任何编码 API。** 真正编码必须由用户态（Allwinner libcedar/MPP/vencoder）
> 通过 mmap 直接编程 VENC 寄存器完成；而 5.4 BSP 的 rootfs/SDK **没有附带这个用户态库**。

---

## 0. 结论速览

| 问题 | 结论 | 证据 |
|---|---|---|
| 驱动里有编码相关代码吗？ | **有“资源管理”级支持**：`VE_LOCK_VENC`、`en_irq_flag/value`、`IOCTL_WAIT_VE_EN`、编码 IRQ 分支（avc enc @0xb00） | `cedar_ve.h:85`、`cedar_ve.c:220-221,330-367,1268-1281` |
| 驱动能直接编 H.264 吗？ | **不能**：没有任务提交、没有码控/参数、没有码流输出、没有 V4L2 M2M | 全文件 `encode` 仅 2 处注释；无 `v4l2_*` 注册 |
| 那编码靠什么？ | 用户态 mmap `0x01C0E000` 寄存器，自己写 VENC 寄存器；内核只负责时钟/复位/IRQ/内存 | `MACC_REGS_BASE=0x01C0E000`、`cedardev_mmap()` |
| 5.4 BSP 自带这个用户态吗？ | **没有**：SDK 里没有 `libcedar`/`libvencoder`（只有 sun60iw2/sun55iw3 用 `libcedarc`） | `vendor/orangepi-build/external` grep |
| H616 的 VENC 寄存器布局与驱动匹配吗？ | **未证实**：驱动是 2013–2016 年的老 VE 布局（0xb00），没有 H616 专用编码代码 | `cedar_ve.c` 版本/注释；DTS 只绑定通用 compatible |
| 能上板直接硬编吗？ | 不能“开箱即用”；需要厂商用户态库 + 参数/寄存器序列 + 实测 | 下文 §5 |

## 1. 驱动定位与绑定

### 1.1 它是什么

- 字符设备 `/dev/cedar_dev`，`unlocked_ioctl = compat_cedardev_ioctl`，`mmap = cedardev_mmap`；
- `MODULE_DESCRIPTION("User mode CEDAR device interface")` —— 官方自己定义为**用户态 CEDAR 接口**；
- 模块名 `cedar_dev`（`sunxi-ve.ko`），Kconfig `VIDEO_ENCODER_DECODER_SUNXI`。

### 1.2 H616/Zero3 确实绑定它

5.4 DTS（`arch/arm64/boot/dts/sunxi/sun50iw9.dtsi:414`）：

```dts
ve: ve@1c0e000 {
    compatible = "allwinner,sunxi-cedar-ve";
    reg = <0x0 0x01c0e000 0x0 0x1000>,
          <0x0 0x03000000 0x0 0x10>,
          <0x0 0x03001000 0x0 0x1000>;
    interrupts = <GIC_SPI 93 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&ccu CLK_BUS_VE>, <&ccu CLK_VE>, <&ccu CLK_MBUS_VE>;
    resets = <&ccu RST_BUS_VE>;
    iommus = <&mmu_aw 3 1>;
};
ve1: ve1@1c0e000 { compatible = "allwinner,sunxi-cedar-ve"; iommus = <&mmu_aw 2 1>; };
```

- 驱动 `sunxi_cedar_probe()` 对 `ve`（alias 0）做 `cedardev_init()`；对 `ve1`（alias 1）**只注册 IOMMU master，直接 return**（`cedar_ve.c:2389-2400`）。
- 两个 IOMMU master（3 与 2）通常对应解码/编码两条通道（具体编号含义需 datasheet 确认）。
- 5.4 `.config` 里 `CONFIG_VIDEO_ENCODER_DECODER_SUNXI=y`（built-in），所以 H616 上 `/dev/cedar_dev` 会存在。

---

## 2. 编码相关的接口（有，但只是底层资源）

从 `cedar_ve.h` 的 ioctl 列表（第 23–80 行）与 `cedar_ve.c` 的实现看，编码相关的是：

| 接口 | 作用 | 证据 |
|---|---|---|
| `mmap(/dev/cedar_dev)` | 把 **VE 寄存器窗口 0x01C0E000** 映射到用户态（uncached） | `cedar_ve.c:80,1786-1806` |
| `IOCTL_ENABLE_VE` / `IOCTL_DISABLE_VE` | 开/关 VE 时钟（编码/解码共用） | `cedar_ve.c:1300-1313` |
| `IOCTL_RESET_VE` | 复位 VE | `cedar_ve.c:1315-1318` |
| `IOCTL_SET_VE_FREQ` | 设 VE 频率（编码性能相关） | `cedar_ve.c:1334-1345` |
| `IOCTL_WAIT_VE_EN` | **等待编码引擎 IRQ**（参数为超时秒数） | `cedar_ve.c:1268-1281` |
| `IOCTL_GET_LOCK` + `VE_LOCK_VENC` | 编码引擎互斥锁（多进程仲裁） | `cedar_ve.h:85`、`cedar_ve.c:1398-1420` |
| `IOCTL_ENGINE_REQ/REL` | VE 引擎引用计数/保活 | `cedar_ve.c:1132-1216` |
| `IOCTL_MAP_DMA_BUF` / `GET_IOMMU_ADDR` | 把用户缓冲区映射成 VENC 可访问的 IOMMU 地址 | `cedar_ve.c:1530-1590` |
| `IOCTL_FLUSH_CACHE_RANGE` | 刷新 CPU cache（编码输入/输出一致性） | `cedar_ve.c:1597-1620` |
| `IOCTL_POWER_SETUP/SHUTDOWN` | 电源管理 | `cedar_ve.h:80-81` |
| `IOCTL_GET_ENV_INFO` | 5.4 里**返回全 0**（注释：仅兼容旧用户态） | `cedar_ve.c:1357-1368` |

**注意：没有**“提交编码任务/设置码率/GOP/profile/取码流”的 ioctl。也就是说，内核不知道 H.264 语法，
只负责“把寄存器给用户态、给时钟、给 IRQ、给内存”。

### 2.1 编码 IRQ 是真实存在的

`VideoEngineInterupt()` 根据 `regs_ve+0x0` 的 module select 位判断引擎：

```c
if (modual_sel & (3<<6)) {
    if (modual_sel & (1<<7)) {
        /*avc enc*/
        status_reg = regs_ve + 0xb00 + 0x1c;
        ctrl_reg   = regs_ve + 0xb00 + 0x14;
        ...
        cedar_devp->en_irq_flag = 1;   /* 唤醒 IOCTL_WAIT_VE_EN */
    } else { /* isp */ }
}
```

（`cedar_ve.c:330-367`）

- 驱动**预期 H.264 编码器在 0xb00 寄存器块、module select bit7**；
- 这是老 VE（A10/A20 时代）的布局；**H616 的 VENC 是否仍是 0xb00/bit7，kernel 树里没有证据**。
- 驱动对编码只有这个 IRQ 分支 + 标志位，没有其他编码逻辑。

## 3. “没有编码实现”的硬证据

1. 全文件 `encode` 只出现 **2 次**，都是 `en_irq_flag/value` 的注释（`cedar_ve.c:220-221`）；
2. 没有 `v4l2_`/`video_register_device`/`v4l2_m2m`，不是 V4L2 编码器；
3. 没有编码任务结构/参数（`struct cedarv_engine_task` 是解码任务队列，带 `picture_info` 等解码字段）；
4. `IOCTL_WAIT_VE_EN` 只等待一个全局 IRQ 标志，没有 per-task 完成/码流长度/错误码；
5. Kconfig 帮助写的是 “driver for sunxi video **decoder**, including h264/mpeg4/...”，编码只是硬件共享资源。

---

## 4. 用户态缺口：SDK 里没有编码库

- 5.4 BSP 的 kernel 只提供 `/dev/cedar_dev`；Allwinner 的编码实现通常在用户态
  `libcedar`/`libvencoder`（Android）或 MPP（Linux）里。
- 本仓库的 `orangepi-build` 里：
  - `libcedarc` 只出现在 **sun60iw2 / sun55iw3**（更新的 SoC）的 family 配置；
  - **sun50iw9（H616/Zero3）没有任何 libcedar/libvencoder 包**；
  - `external/packages` 里也没有 H616 编码 demo。
- 结论：5.4 镜像开箱只有 `/dev/cedar_dev`，没有能调用它的编码用户态；要硬编必须从厂商另行获取
  （MPP/libvencoder + 示例 + License），或自己写寄存器级编码器（不现实）。

---

## 5. 如果要做硬编，必须补齐什么

| 缺口 | 具体内容 | 验证方式 |
|---|---|---|
| 用户态库 | `libvencoder`/MPP 的 so + 头文件 + H.264 1080p30 示例 | 编译厂商 demo，跑通一次编码 |
| 寄存器序列 | H616 VENC 初始化/码控/中断清除/复位序列 | 对照 datasheet 或厂商代码，读 0xb00 寄存器 |
| 缓冲/IOMMU | 输入 YUV/输出码流的 DMA-BUF 与 IOMMU 地址 | `IOCTL_MAP_DMA_BUF` + `GET_IOMMU_ADDR` |
| 并发/时钟 | VENC 与 VDEC 共享 VE/SRAM/时钟的约束 | 同时解码+编码压测 |
| 参数 | profile/level、GOP、CBR/VBR、最大码率 | 与 x264 同码率对比画质 |
| H616 适配 | 驱动是 2013–2016 老布局，H616 可能不同 | 读 VENC ID/寄存器，或厂商确认 |

**最小验证脚本思路**（有 root、在 5.4 镜像上）：

```bash
ls -l /dev/cedar_dev
# 用厂商 demo（若有）:
./venc_demo --width 1920 --height 1080 --fps 30 --bitrate 4000000 --out out.h264
# 同时观察:
cat /proc/interrupts | grep -i cedar
top -H -p $(pgrep venc_demo)
```

没有厂商 demo 时，只能自己 mmap 寄存器做 bring-up；这已经属于“写编码器”而不是“用驱动”。

---

## 6. 对方案的影响

- **“cedar device 包含编码能力”这句话要分两层**：
  - 底层：**是**，它把 VENC 寄存器、IRQ、时钟、IOMMU 暴露给用户态；
  - 高层：**否**，它没有编码 API/实现，不能直接 `ffmpeg -c:v h264_cedar`。
- 因此：
  1. 官方 6.1 没有这个驱动 → 完全无硬编；
  2. 5.4 有驱动但无用户态 → **也不能开箱硬编**；
  3. 唯一可行路径是“厂商 5.4 BSP + 厂商编码库/demo”，且要验证 H616 寄存器布局与稳定性；
  4. 如果拿不到厂商库，就把 H618 当“无硬编”用（软件 x264，480p20–25fps）。
