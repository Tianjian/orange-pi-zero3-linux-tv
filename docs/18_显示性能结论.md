# 18 · Zero3 Linux 视频显示的硬件/软件路径结论

日期：2026-11-05
板端：Orange Pi Zero3 / H618 / Debian 12 / 6.1.31-sun50iw9

## 1. 硬件解码本身很快

用本地 720×1280 H.264 30fps、900 帧测试：

```text
filesrc ! qtdemux ! h264parse ! v4l2slh264dec ! fakesink sync=false
real 2.0s  -> 约 450 fps
```

cedrus / v4l2slh264dec 硬件解码没有问题。

## 2. 瓶颈在“转 RGB + 缩放 + 写显示”

```text
v4l2slh264dec ! videoconvert ! BGRx ! fakesink   # 900 帧 >35s，约 25fps
v4l2slh264dec ! videoscale(480p) ! videoconvert ! BGRx  # 900 帧约 30s，约 30fps
```

- H.264 解码后是 NV12；Linux 侧 `fbdevsink` / DE primary 只接受 RGB；
- `videoconvert` 单/多线程在 A53 上约 20–25fps（720p），是实际帧率上限；
- `videoscale add-borders=true` 更慢（计算黑边/DAR）；
- `videobox` 在本版 GStreamer 对多数尺寸有链接 bug，无法稳定补边。

## 3. DE overlay 层不能扫出

- `plane 31`（YUV overlay）可以被 kmssink 提交（fb 非 0），但 HDMI 上黑屏；
- `plane 37`（primary）是唯一实际扫出的层，只支持 RGB，不支持 NV12；
- 因此无法“硬件解码 → NV12 直出 → 硬件缩放/letterbox”；
- 无 fbdev 内核、modetest 点 CRTC、zpos 调整均验证过，overlay 仍不显示。

## 4. gmediarender 的绿色问题

- `decodebin`/playbin 默认选的硬件解码输出被当成不匹配格式，整屏绿色；
- 手工显式 `h264parse ! v4l2slh264dec ! videoconvert` 颜色正常；
- 桥接方案（gmediarender 只做 UPnP，独立 gst-launch 出画面）颜色正常，但仍受第 2 条转换瓶颈限制。

## 5. 当前可用状态

- 旧 fbdev 内核 + gmediarender + `avdec_h264` + 720p `fbdevsink`；
- 颜色正确，帧率约 20–25fps（720p，含黑边）；
- 服务：`opiz3-renderer.service`；桥接 `opiz3-bridge` 已禁用。

## 6. 现实选项

| 方案 | 结果 | 代价 |
|---|---|---|
| Linux 720p 软件解码（当前） | 颜色正确，约 20–25fps | 不够流畅，但保留 DLNA/SSH/GPIO |
| Linux 480p 无黑边 | 约 30fps | 竖屏被拉伸/画质低 |
| Android 12 TV | 厂商显示/GPU/VPU 管线，流畅 | 放弃 Debian/Linux 开发环境 |
| RK3566/RK3588 + Linux | 标准 V4L2/DRM、硬件缩放 | 换板 |

**结论**：在 H618 的 Linux 6.1 + 这块 DE 上，无法做到“流畅的 720p/1080p + 正确比例 + 纯硬件路径”。
如果目标是视频 App 投屏的“电视 demo”，Android TV 是更现实的选择；如果要继续 Linux，
只能在 720p/20–25fps、480p/30fps（拉伸）之间取舍。

## 7. DRM overlay + DE3.3 spike 结果

判定性实验（no-fbdev 内核、modetest 点 CRTC）：

| 测试 | 结果 |
|---|---|
| UI overlay `plane 41` + RGB | ✅ 彩条正常 |
| VI overlay `plane 31` + RGB | ✅ 彩条正常 |
| VI overlay `plane 31` + NV12 | ❌ 黑屏 |

说明 overlay/mixer 路由正常，问题集中在 **VI 层的 NV12/YUV/CSC 路径**。

已尝试的 CSC 补丁（均未解决 NV12 黑屏）：

1. vendor 原实现：channel base - 0x200；
2. vendor `is_de33` 的 CSC 使能缺失，补 blender CSC_CTL；
3. 上游 DE33 CSC 布局：`DE33_CCSC_BASE=0x800 + channel*0x20000`，
   `SUN50I_CSC_COEFF(base,i)=base+0x04+4*i`，15 项系数，`CSC_CTRL` 在 base+0。

结论：vendor 6.1 的 DE3.3 **VI 层格式/缩放/CSC 整体是半成品**，不是单个 CSC 寄存器能修好；
需要移植上游 DE33 的 layer/mixer/CSC 系列（Ryan Walklin/Jernej Skrabec），或拿全志 DE3.3 寄存器文档。
